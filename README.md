## 1. 项目简介

- 应用场景：校园无人车/机器人配送，多车协同完成取货与送货任务。
- 系统类型：多智能体系统，包含环境、车辆、订单、调度等智能体。
- 主要能力：
  - 核心调度策略（课程实验版）：贪心最近（GREEDY_NEAREST）、拍卖机制(CNP, AUCTION_CNP)、强化学习调度（RL_SCHEDULER，内部可切换 DQN/PPO 等）。
  - 实时路径规划：A*、时空 A*、多智能体路径规划（MAPF）。
  - 智能能量管理：非线性电量消耗、三级充电决策、充电站容量管理与排队系统。
  - 可视化：本地 GUI 仿真 + 基于 FastAPI + Vue3 的 Web 监控面板，实时显示充电站状态、车辆电量、拍卖日志，以及在 Canvas 上用编号标注的订单取/送货点。
  - 数据记录：支持 CSV 导出、JSON 快照和性能图表生成。

适用用途：

- 多智能体系统 / 强化学习 / 调度与路径规划 课程作业
- 教学演示与答辩展示
- 算法原型验证与对比实验

## 3. 环境与安装

### 3.1 环境要求

- Python 3.8+
- 操作系统：Windows / macOS / Linux
- 可选：NVIDIA GPU（RL 训练加速）
- Node.js 16+（用于 Web 前端）

### 3.2 安装步骤

```bash
# 克隆项目
git clone https://github.com/Dictatora0/CampusFleet-AI.git
cd CampusFleet-AI

# 创建并激活虚拟环境
python -m venv venv
source venv/bin/activate  # Windows: venv\Scripts\activate

# 安装基础依赖
pip install -r requirements.txt

# 如需 Web 平台
pip install -r requirements-web.txt

# 如需强化学习训练
pip install -r requirements-rl.txt
```

```bash
# 在项目根目录，确保虚拟环境已激活
cd CampusFleet-AI

# 创建仿真实例
curl -X POST http://localhost:8001/api/simulation/create \
  -H "Content-Type: application/json" \
  -d '{
    "grid_size": 10,
    "num_cars": 4,
    "strategy": "GREEDY_NEAREST",
    "enable_logging": true
  }'

# 添加若干随机订单
for i in {1..8}; do
  curl -X POST http://localhost:8001/api/orders/random

done

# 启动仿真（自动步进）
curl -X POST http://localhost:8001/api/simulation/control \
  -H "Content-Type: application/json" \
  -d '{"command": "start", "params": {"auto_step": true}}'
```

## 5. 功能概览

### 5.1 多智能体架构

系统中主要智能体：

- 环境智能体（Environment）：网格地图、障碍物、位置查询。
- 车辆智能体（Vehicle）：执行配送任务，具备感知、决策、行动能力。
- 订单智能体（Order）：管理订单生命周期与统计信息。
- 调度智能体（Scheduler）：集中式任务分配与协作决策。

### 5.2 调度与路径规划

- 调度策略（课程实验版 - 3 个核心 AI 策略）：
  - `GREEDY_NEAREST`：贪心最近车辆（启发式基线）
  - `AUCTION_CNP`：拍卖机制，基于合同网协议（Contract Net Protocol, CNP）的多智能体竞标
  - `RL_SCHEDULER`：强化学习调度（内部支持 DQN / PPO 等实现）
- 高级/扩展策略（研究版，可选）：
  - 负载均衡（BALANCED_LOAD）、匈牙利算法（HUNGARIAN）、VRP 拼单（VRP_BATCHING）、MAPF CBS（MAPF_CBS）等算法仍保留在代码与文档中，方便深入研究，但不再作为课程实验的默认入口。

路径规划：

- A\* 最短路径搜索
- 时空 A\* 与 MAPF 协调无碰撞路径
- 避碰策略与死锁避免

### 5.3 智能能量管理与充电系统

系统实现了完整的电池管理和充电站系统，模拟真实无人车的能量约束。

#### 5.3.1 非线性电量消耗模型

车辆电量消耗不再是固定值，而是根据实际工况动态计算：

**消耗公式：**

```
total_consumption = base_rate × (1 + 载货惩罚 + 速度惩罚)
载货惩罚 = 0.3 × 当前载货量
速度惩罚 = 0.2 × max(0, 速度 - 1)
```

**示例：**

- 空载低速（载 0 个订单，速度 1）：消耗 1.0 单位/步
- 载 1 个订单（速度 1）：消耗 1.3 单位/步（+30%）
- 载 2 个订单+速度 2 倍：消耗 1.8 单位/步（+80%）

#### 5.3.2 三级充电决策系统

车辆具备智能充电决策能力，根据电量和任务状态自动判断是否需要充电：

| 优先级      | 电量阈值 | 触发条件              | 行为                             |
| ----------- | -------- | --------------------- | -------------------------------- |
| 🚨 严重低电 | < 10%    | 任何状态              | 立即放弃当前任务，强制前往充电站 |
| ⚠️ 主动充电 | < 30%    | 空闲状态              | 寻找最近充电站，主动充电         |
| 💡 机会充电 | < 50%    | 空闲 + 距充电站 ≤3 格 | 顺路充电（类似"加油顺便加一下"） |

**决策示例：**

```python
# 车辆1电量8%，正在送货
→ 🚨 严重低电检测
→ 取消订单#7
→ 寻找最近充电站
→ 前往充电站(0, 11)

# 车辆3电量45%，空闲，距充电站2格
→ 💡 机会充电检测
→ 前往充电站(14, 7)
```

#### 5.3.3 充电站容量管理与排队系统

每个充电站具备真实的容量限制和排队机制：

**充电站属性：**

- 容量：2 个充电位（可配置）
- 充电速率：5 单位/步（可配置）
- 排队队列：FIFO 先进先出
- 使用率统计：实时计算并可视化

**智能选站算法：**

```python
score = 距离 × 1.0 + 排队长度 × 5.0 - 空位奖励
# 选择score最低的充电站
```

**排队流程：**

1. 车辆请求充电
2. 如有空位 → 立即分配
3. 如已满 → 加入排队队列
4. 前车充电完成 → 自动分配给队首车辆

#### 5.3.4 Web 前端可视化

充电系统在 Web 界面实时可视化：

**充电站显示：**

- ⚡ 闪电图标，位于地图边缘
- 背景颜色根据使用率变化：
  - 🟢 绿色：使用率 < 50%（空闲）
  - 🟡 黄色：使用率 50-80%（繁忙）
  - 🔴 红色：使用率 ≥ 80%（拥挤）

**车辆电量颜色：**

- 🟢 绿色：电量 ≥ 50%（充足）
- 🟡 黄色：电量 30-50%（中等）
- 🟠 橙色：电量 10-30%（低）
- 🔴 红色：电量 < 10%（严重低电）

**交互式 Tooltip：**

- 鼠标悬停充电站：显示可用充电位、排队长度、等待队列
- 鼠标悬停车辆：显示电量百分比、状态、当前订单

#### 5.2.1 调度策略详细说明

本项目在课程实验版中重点提供 3 种**核心 AI 调度策略**：

- GREEDY_NEAREST：贪心最近车辆，作为启发式基线；
- AUCTION_CNP：基于合同网协议的拍卖机制，多智能体分布式调度；
- RL_SCHEDULER：统一的强化学习调度入口（内部可接入 DQN / PPO 等 RL 智能体）。

同时，完整研究版中曾使用的 BALANCED_LOAD / HUNGARIAN / VRP_BATCHING / MAPF_CBS 等策略，当前在代码与文档中保留为**扩展/高级选项**，便于后续科研与算法对比实验使用。

##### 1. GREEDY_NEAREST（贪心最近车辆）

**策略名称**: `GREEDY_NEAREST`

**算法原理**:

- 为每个待分配订单选择距离取货点最近的空闲车辆
- 使用曼哈顿距离（Manhattan Distance）计算距离
- 遵循"先到先得"原则，快速响应

**适用场景**:

- 订单密度较低，车辆较多
- 需要快速响应时间
- 实时性要求高的场景

**优点**:

- ✅ 计算速度快，O(n×m) 时间复杂度（n=车辆数，m=订单数）
- ✅ 响应时间短，订单分配延迟低
- ✅ 实现简单，易于理解和调试

**缺点**:

- ❌ 可能导致部分车辆过载，其他车辆空闲
- ❌ 不考虑全局最优，长期效率可能不是最佳
- ❌ 对于高密度订单场景性能下降

**参数配置**:

```python
# 代码中使用
strategy = SchedulingStrategy.GREEDY_NEAREST

# API调用
"strategy": "GREEDY_NEAREST"

# 命令行参数
./run_experiment.sh 10 4 10 GREEDY_NEAREST
```

**性能指标**（典型值）:

- 平均响应时间: 1-3 步
- 车辆利用率: 60-75%
- 订单完成率: 85-95%

##### 2. AUCTION_CNP（拍卖机制-合同网协议）

**策略名称**: `AUCTION_CNP`

**算法原理**:

- 采用合同网协议（Contract Net Protocol, CNP）实现分布式任务分配
- 订单作为“拍卖品”，附近车辆作为“竞标者”
- 每辆车根据自身状态（位置、电量、任务队列长度等）计算竞标成本并参与拍卖
- 拍卖流程分为四个阶段：任务公告 → 竞标 → 中标选择 → 授予（Award）

**竞标成本示例**:

- 距离成本：到取货点距离 × 2.0 + 配送距离 × 1.0
- 电量惩罚：
  - 电量 <30%：施加较大惩罚系数
  - 电量 <50%：施加中等惩罚系数
- 负载惩罚：当前任务队列中待处理订单数 × 10
- 若车辆电量不足以完成“去取货 + 送达 + 回充电站”的全程，则视为放弃本次竞标

**适用场景**:

- 需要展示多智能体协商、竞标和任务分配过程的课程实验
- 希望在调度决策中同时考虑距离、电量和车辆负载等多种因素
- 需要对“为什么是这辆车中标”给出可解释的示例与日志

**优点**:

- ✅ 符合多智能体系统设计理念，决策分布到各个车辆智能体
- ✅ 将电量、任务负载等约束自然整合到成本函数中，更贴近真实调度场景
- ✅ 拍卖过程有详细日志和前端可视化，便于教学讲解与结果分析

**缺点**:

- ❌ 相比简单贪心，计算和通信开销更高
- ❌ 成本函数中的权重（距离、电量、负载）需要根据场景进行调参

**参数配置**:

```python
# 代码中使用
strategy = SchedulingStrategy.AUCTION_CNP

# API 调用
"strategy": "AUCTION_CNP"
```

**相关工具与可视化**:

- 后端会记录拍卖过程日志，可通过 `/api/auction/logs` 获取
- 前端 Web 仿真提供拍卖日志面板（Auction Log Panel），实时展示每一轮竞标结果和最近多轮拍卖统计
- Web 仿真预设 `拍卖机制（多智能体）` 与 `./debug_web.sh` 脚本默认使用 `AUCTION_CNP`，打开页面即可看到实时拍卖日志
- `test_auction_mechanism.py` 可用于对拍卖逻辑进行单元/集成测试

##### 3. RL_SCHEDULER（强化学习调度）

**策略名称**: `RL_SCHEDULER`

**算法原理**:

- 使用深度强化学习（Deep RL）学习“订单 → 车辆”的调度策略
- 状态通常包含：车辆位置与电量、订单位置与数量、系统当前负载等信息
- 动作为：在候选车辆中选择一辆去执行当前订单
- 通过长期累计奖励（例如：更短的平均完成时间、更高的完成率等综合指标）来优化策略

**实现说明**:

- 项目中将所有 RL 调度统一封装为 `RL_SCHEDULER`，内部可接入 DQN / Double DQN / PPO 等算法实现
- 强化学习训练与对比实验脚本位于 `experiments/` 目录（如 `rl_comparison.py` 等）
- 在推理阶段，调度器调用已训练好的 RL 模型进行决策，不再依赖手工设计的启发式规则

**适用场景**:

- 需要展示“AI 自主学习调度策略”的课程作业或答辩展示
- 环境复杂、规则难以手工穷举，希望通过数据驱动学习出更优调度策略
- 希望在长期运行下优化全局指标（如平均等待时间、车辆利用率等）

**优点**:

- ✅ 可自动从数据中学习复杂调度策略，减少手工规则设计工作量
- ✅ 能同时考虑多种因素（位置、电量、历史轨迹等），在充分训练后有潜力超过简单启发式

**缺点**:

- ❌ 训练成本较高，需要较长时间和足够的交互数据
- ❌ 策略可解释性较弱，相比贪心/拍卖不够直观
- ❌ 对超参数和奖励设计较为敏感

**参数配置**:

```python
# 代码中使用
strategy = SchedulingStrategy.RL_SCHEDULER

# API 调用
"strategy": "RL_SCHEDULER"
```

**实验与验证**:

- 可使用 `experiments/` 目录中的脚本进行 RL 与非 RL 策略的对比实验（可选）
- 结合 `run_experiment.sh` 收集数据，并在 Web 多智能体监控面板中观察性能指标变化

##### （扩展）BALANCED_LOAD（负载均衡）

**策略名称**: `BALANCED_LOAD`

**算法原理**:

- 考虑每辆车的当前任务负载
- 优先分配给任务最少的空闲车辆
- 在距离和负载之间寻求平衡

**适用场景**:

- 长时间连续运行的系统
- 订单持续到达的场景
- 需要均衡车辆磨损和能耗

**优点**:

- ✅ 车辆利用率更均衡，避免过载
- ✅ 适合长期运行，车辆寿命更长
- ✅ 系统稳定性好，不易出现单点过载

**缺点**:

- ❌ 可能牺牲部分响应速度
- ❌ 某些订单可能被分配给较远的车辆
- ❌ 计算开销略高于贪心策略

**参数配置**:

```python
# 代码中使用
strategy = SchedulingStrategy.BALANCED_LOAD

# API调用
"strategy": "BALANCED_LOAD"

# 命令行参数
./run_experiment.sh 15 6 20 BALANCED_LOAD
```

**性能指标**（典型值）:

- 平均响应时间: 2-4 步
- 车辆利用率: 75-85%
- 订单完成率: 90-95%
- 车辆负载标准差: 较低

##### （扩展）HUNGARIAN（匈牙利算法）

**策略名称**: `HUNGARIAN`

**算法原理**:

- 基于匈牙利算法（Hungarian Algorithm）求解最优分配问题
- 构建成本矩阵（车辆-订单距离）
- 求解全局最小成本匹配

**适用场景**:

- 批量订单同时到达
- 对全局效率要求高
- 允许稍长的计算时间

**优点**:

- ✅ 理论上的全局最优分配
- ✅ 总体配送距离最短
- ✅ 适合批量处理场景

**缺点**:

- ❌ 计算复杂度较高 O(n³)
- ❌ 实时性略差
- ❌ 车辆数和订单数较多时性能下降

**参数配置**:

```python
# 代码中使用
strategy = SchedulingStrategy.HUNGARIAN

# API调用
"strategy": "HUNGARIAN"

# 命令行参数
./run_experiment.sh 20 8 20 HUNGARIAN
```

**性能指标**（典型值）:

- 平均响应时间: 3-5 步
- 车辆利用率: 70-80%
- 订单完成率: 92-98%
- 总配送距离: 最优

**技术细节**:

- 使用 `scipy.optimize.linear_sum_assignment` 实现
- 成本矩阵基于曼哈顿距离
- 支持不完全匹配（车辆数 ≠ 订单数）

##### （扩展）VRP_BATCHING（车辆路径问题拼单优化）

**策略名称**: `VRP_BATCHING`

**算法原理**:

- 基于车辆路径问题（Vehicle Routing Problem, VRP）
- 允许单车同时处理多个订单
- 优化订单批次和配送路线

**适用场景**:

- 订单密集区域
- 允许批量配送
- 注重总体效率而非单个订单时间

**优点**:

- ✅ 支持多订单拼单，提高效率
- ✅ 减少总行驶距离
- ✅ 适合密集订单场景

**缺点**:

- ❌ 单个订单等待时间可能较长
- ❌ 计算复杂度高
- ❌ 需要足够的订单密度才能发挥优势

**参数配置**:

```python
# 代码中使用
strategy = SchedulingStrategy.VRP_BATCHING

# API调用
"strategy": "VRP_BATCHING"

# 命令行参数
./run_experiment.sh 15 5 25 VRP_BATCHING
```

**性能指标**（典型值）:

- 平均响应时间: 4-8 步
- 车辆利用率: 80-90%
- 订单完成率: 88-95%
- 每车平均订单数: 2-3

**推荐参数**:

- 网格大小: 15×15 或更大
- 订单数: 20+
- 车辆数: 4-6

##### （扩展）MAPF_CBS（多智能体路径规划-冲突感知搜索）

**策略名称**: `MAPF_CBS`

**算法原理**:

- 基于冲突感知搜索（Conflict-Based Search, CBS）
- 协调多车辆路径，避免冲突和死锁
- 时空路径规划，考虑时间维度

**适用场景**:

- 车辆密度高的环境
- 狭窄通道或复杂地图
- 需要避免路径冲突

**优点**:

- ✅ 无碰撞路径规划
- ✅ 避免死锁情况
- ✅ 多车协调性能好

**缺点**:

- ❌ 计算开销最大
- ❌ 实时性较差
- ❌ 需要较多内存存储时空路径

**参数配置**:

```python
# 代码中使用
strategy = SchedulingStrategy.MAPF_CBS

# API调用
"strategy": "MAPF_CBS"

# 命令行参数
./run_experiment.sh 12 6 15 MAPF_CBS
```

**性能指标**（典型值）:

- 平均响应时间: 4-7 步
- 车辆利用率: 65-75%
- 订单完成率: 85-92%
- 路径冲突率: <1%

**技术细节**:

- 使用时空 A*（Space-Time A*）规划路径
- CBS 算法协调多车辆路径
- 支持动态重规划

#### 5.2.2 策略选择建议

根据不同场景选择合适的策略（课程实验版推荐）：

| 场景              | 推荐策略                      | 原因                           |
| ----------------- | ----------------------------- | ------------------------------ |

| 多智能体协商展示  | AUCTION_CNP                   | 展示合同网协议与车辆竞标过程   |
| AI 智能调度展示   | RL_SCHEDULER                  | 展示深度强化学习的自适应能力   |
| 课堂教学/课程答辩 | GREEDY_NEAREST 或 AUCTION_CNP | 现象直观、便于讲解与截屏       |
| 高级研究（可选）  | RL_SCHEDULER                  | 适合做 RL 算法对比与论文级实验 |

**策略对比实验示例（可选）**:

```bash

./run_experiment.sh 15 6 20 RL_SCHEDULER
```

**性能对比维度**:

- 响应时间：订单从创建到分配的平均时间
- 完成率：成功完成订单的百分比
- 车辆利用率：活跃车辆占总车辆的比例
- 总行驶距离：所有车辆行驶的总距离
- 计算开销：策略计算所需的时间

**待处理订单** (Pending Orders)

- **主数值**: 车辆智能体总数
- **来源**: 后端 `GET /api/agents/status` 返回的 `agents.vehicles` 数组长度
- **活跃数**: 状态为 `busy` 的车辆数量
- **含义**: 展示系统中车辆的总体配置和当前工作状态

**订单智能体卡片** (📦 图标)

- **主数值**: 订单智能体总数
- **来源**: 后端 `agents.orders` 数组长度
- **待处理数**: 状态为 `PENDING` 的订单数
- **含义**: 反映订单总量和待分配情况

**通信消息卡片** (📡 图标)

- **主数值**: 累计通信消息总数
- **来源**: 后端 `GET /api/communication/logs` 的 `total_messages`
- **本轮消息**: 当前步骤的消息数
- **含义**: 展示智能体间通信活跃度

**完成率卡片** (📊 图标)

- **主数值**: 订单完成百分比
- **计算**: (已完成订单数 / 总订单数) × 100%
- **来源**: 后端 `GET /api/performance/metrics` 的 `completion_rate`
- **性能等级**: A-F 等级评价
  - A: ≥90%, B: ≥80%, C: ≥70%, D: ≥60%, F: <60%
- **含义**: 系统整体配送效率指标

##### 左侧：智能体状态面板

**刷新按钮** (蓝色)

- **功能**: 手动刷新智能体状态数据
- **API 调用**: `GET /api/agents/status`
- **自动刷新**: 默认每 2 秒自动刷新一次

**车辆智能体标签页**

每个车辆卡片显示：

- **车辆 ID**: 唯一标识符 (例如: 车辆 #0)
- **状态标签**: 空闲(灰色) / 忙碌(绿色)
- **位置**: 当前网格坐标 (x, y)
  - **来源**: `vehicle.position`
  - **含义**: 车辆在地图上的精确位置
- **感知**: 感知范围（格数）
  - **来源**: `vehicle.perception.range`
  - **含义**: 车辆可探测订单的范围，固定为 5 格
- **决策**: 决策方法
  - **来源**: `vehicle.decision.method`
  - **显示**: "A\* pathfinding"（A 星路径规划算法）
  - **含义**: 车辆使用的路径规划算法
- **行动**: 当前行为
  - **来源**: `vehicle.action.current`
  - **状态**: moving(移动中) / idle(空闲)
  - **含义**: 车辆的当前动作状态
- **已完成**: 完成订单数
  - **来源**: `vehicle.completed_orders`
  - **含义**: 该车辆累计完成的订单总数

**调度智能体标签页**

- **策略**: 当前使用的调度算法
  - **来源**: `agents.scheduler.strategy`
  - **可能值**: GREEDY_NEAREST / HUNGARIAN / VRP_BATCHING / MAPF_CBS
- **总分配**: 累计任务分配次数
  - **来源**: `agents.scheduler.total_assignments`
  - **含义**: 调度器执行过的分配决策总数
- **活跃车辆**: 正在工作的车辆数
  - **来源**: `agents.scheduler.active_vehicles`
- **待分配订单**: 等待分配的订单数
  - **来源**: `agents.scheduler.pending_orders`

**环境智能体标签页**

- **网格大小**: 地图尺寸
  - **来源**: `agents.environment.grid_size`
  - **显示**: N×N（例如 15×15）
- **当前步骤**: 仿真执行的步数
  - **来源**: `agents.environment.current_step`
- **总订单数**: 系统创建的订单总数
  - **来源**: `agents.environment.total_orders`
- **已完成**: 成功配送的订单数
  - **来源**: `agents.environment.completed_orders`

##### 中间：通信日志窗口

**刷新按钮** (蓝色)

- **功能**: 手动刷新通信日志
- **API 调用**: `GET /api/communication/logs`

**通信统计条**

- **状态报告**: 车辆定期向调度器汇报位置和状态
- **任务分配**: 调度器向车辆分配新订单

**日志列表**

每条日志包含：

- **时间戳**: 消息产生的精确时间
- **发送者**: 消息来源智能体（例如: Vehicle-0, Scheduler）
- **箭头**: → 表示消息传递方向
- **接收者**: 消息目标智能体
- **消息内容**: 具体通信内容
  - **位置报告**: "Position: (x, y), Status: idle/busy"
  - **任务分配**: "Assigned Order-{订单 ID}"
- **消息类型**:
  - **状态报告** (灰色边框): 车辆 → 调度器的周期性状态更新
  - **任务分配** (绿色边框): 调度器 → 车辆的订单分配通知
- **数据来源**: 后端 `communication_logs` API
- **更新方式**: 实时追加新消息，显示最近 20 条

##### 右侧：协作决策可视化

**刷新按钮** (蓝色)

- **功能**: 手动刷新协作数据
- **API 调用**: `GET /api/collaboration/decisions`

**协作指标**

**车辆利用率进度条**

- **计算**: (活跃车辆数 / 总车辆数) × 100%
- **来源**: `collaboration_metrics.vehicle_utilization`
- **颜色规则**:
  - 绿色: ≥70%（高利用率）
  - 黄色: 40-70%（中等）
  - 红色: <40%（利用率低）
- **含义**: 反映车队整体工作饱和度

**并行执行数**

- **数值**: 同时执行任务的车辆数量
- **来源**: `collaboration_metrics.parallel_execution`
- **含义**: 系统并发处理能力的实时指标

**当前分配列表**

每个分配项显示：

- **车辆 ID → 订单 ID**: 分配关系
- **距离取货点**: 曼哈顿距离（格数）
  - **计算**: |车辆 x - 取货点 x| + |车辆 y - 取货点 y|
  - **来源**: 后端实时计算
- **预计步数**: 车辆到达取货点所需步数
  - **来源**: `eta_steps`（车辆当前路径长度）
- **决策理由**: "Optimal assignment"（最优分配）
- **数据来源**: 后端 `assignments` 数组
- **空状态**: 显示"暂无活跃分配"当所有车辆空闲时

##### 底部：性能指标面板

**刷新按钮** (蓝色)

- **功能**: 手动刷新性能数据
- **API 调用**: `GET /api/performance/metrics`

**核心指标**

**完成率**

- **显示**: 百分比进度条 + 数值
- **计算**: (已完成订单 / 总订单) × 100%
- **来源**: `metrics.completion_rate`
- **颜色**: 根据完成率显示不同颜色

**已完成订单**

- **数值**: 成功配送的订单绝对数量
- **来源**: `metrics.completed_orders`

**总订单数**

- **数值**: 系统创建的所有订单总数
- **来源**: `metrics.total_orders`

**待处理订单**

- **数值**: 未完成（待分配+进行中）的订单数
- **来源**: `metrics.pending_orders`

**车辆利用率**

- **显示**: 百分比
- **来源**: `metrics.vehicle_utilization`

**性能等级**

- **显示**: A / B / C / D / F 大字母评级
- **颜色**:
  - A/B: 绿色（优秀/良好）
  - C: 黄色（中等）
  - D/F: 红色（较差/不及格）
- **来源**: 后端 `performance_grade` 综合评估

#### 5.4.3 数据更新机制

**自动刷新**

- 多智能体监控面板默认每 2 秒自动调用 API 更新数据
- 使用 `setInterval` 定时器实现
- 可通过各面板的"刷新"按钮手动立即更新

**WebSocket 实时推送**

- 建立 `ws://localhost:8001/ws/simulation` 连接
- 服务端主动推送仿真状态变化
- 前端收到推送后更新可视化显示
- 连接状态在顶部导航栏显示（绿点=已连接，红点=断开）

**数据流向**

```
后端API ──→ HTTP请求 ──→ 前端Store ──→ Vue组件 ──→ 用户界面
   ↓
WebSocket ──→ 实时推送 ──→ 前端监听 ──→ 状态更新 ──→ 界面刷新
```

#### 5.4.4 常见操作流程

**标准实验流程**:

1. 访问仿真控制台 (`/`)
2. 选择预设配置（如"中等规模演示"）
3. 点击"创建仿真"
4. 添加 3-5 个随机订单
5. 点击"启动"开始自动仿真
6. 切换到多智能体监控页面 (`/multi-agent`)
7. 观察各指标变化，截取关键截图
8. 仿真稳定运行后点击"停止"
9. 导出数据用于分析

**调试观察流程**:

1. 创建小规模仿真（10×10, 4 车）
2. 添加 1-2 个订单
3. 使用"单步"按钮逐步执行
4. 在智能体状态面板观察每步变化
5. 在通信日志查看消息交互
6. 在 Canvas 上查看路径规划

**性能测试流程**:

1. 使用"大规模仿真"预设
2. 添加 10 个以上订单
3. 启动仿真并运行至少 50 步
4. 在性能指标面板记录完成率
5. 观察车辆利用率变化趋势
6. 导出 CSV 数据进行详细分析

## 6. 实验与评估

### 6.1 多智能体系统功能展示实验（推荐）

本实验面向课程作业与系统展示，重点是**系统功能、协作机制、Web 可视化和自动化数据采集**，不强调算法对比。

完整步骤整理在：`assignment_submission/实验步骤.md`，这里给出概要版流程：

#### 6.1.1 多场景 GUI 功能演示

通过 `run_with_gui.py` 在不同规模与策略下运行仿真，展示：

- 小规模基础场景：4 车 + 少量订单，展示基本协作与路径规划。
- 中等规模场景：6 车 + 更多订单，展示系统扩展性与车辆利用率。
- AI 调度场景：使用 `dqn_inference` 策略，展示强化学习调度在系统中的实际效果（作为一种策略，而非算法对比实验）。

典型命令示例：

```bash
# 场景 1：小规模基础功能
python run_with_gui.py --strategy greedy --cars 4 --size 10 --fps 3

# 场景 2：中等规模扩展性
python run_with_gui.py --strategy balanced --cars 6 --size 15 --fps 4

# 场景 3：AI 智能调度
python run_with_gui.py --strategy dqn_inference --cars 5 --size 12 --fps 3
```

建议在每个场景中手动截取 GUI 截图，保存到 `assignment_data/screenshots/` 用于报告与展示。

#### 6.1.2 Web 多智能体监控与协作可视化

结合第 4.2 节的步骤，通过 Web 多智能体监控页面展示：

- 顶部统计卡片：整体负载与完成率。
- 智能体状态面板：车辆 / 调度 / 环境三类智能体的实时状态。
- 通信日志窗口：任务分配与状态报告的消息流。
- 协作决策可视化：任务分配关系、车辆利用率、并行执行情况。

建议在仿真运行稳定后，截取以下 3–4 张关键截图：

- 完整监控面板
- 某辆车的状态详情
- 通信日志高峰时刻
- 协作决策与车辆利用率面板

#### 6.1.3 自动化数据采集与图表生成

为避免手工操作出错，推荐使用自动化脚本 `run_experiment.sh` 完成数据采集与图表生成（详见 `README_AUTO_EXPERIMENT.md`）：

```bash
source venv/bin/activate
./run_experiment.sh
```

脚本会：

- 在 `assignment_data/` 下创建统一的数据与图表目录结构。
- 自动启动 Web 后端与前端，并创建仿真、添加订单、运行一段时间。
- 在多个时间点调用 Web API 采集性能指标与协作数据（JSON）。
- 通过内置 Python 脚本生成 4 张高分辨率图表：
  - 完成率随时间变化
  - 车辆利用率变化
  - 最终订单状态分布
  - 综合性能雷达图
- 生成一份 `experiment_summary.txt`，汇总关键指标与文件列表。

最终，你可以直接从以下位置整理报告素材：

- `assignment_data/plots/`：性能分析图表（可直接插入报告）。
- `assignment_data/csv_exports/simulation_frames.csv`：完整运行日志，可做进一步统计分析。
- `assignment_data/json_data/*.json`：多时刻性能、智能体状态、协作决策与通信日志快照。
- `assignment_data/screenshots/`：GUI + Web 截图（需要手动保存）。

> 推荐写作方式：以“系统功能演示 + Web 可视化 + 自动化数据采集”为主线，只在需要时简要提及使用了强化学习调度策略，而不展开算法对比。

### 6.2 强化学习对比实验（可选，高级）

如果需要从科研或算法验证角度，对比不同 RL 调度策略（如 Standard DQN 与 Double DQN），可以使用 `experiments/` 目录中的脚本：

该部分会运行较长时间，仅在需要撰写强化学习相关论文或深入算法分析时使用。详细实验设计、输出文件结构与图表说明参见：

- `experiments/README_RIGOROUS_EXPERIMENT.md`
